# 0003 — Operator experience

> Builds on [0001_SPEC.md](0001_SPEC.md) §11 (Public API and CLI), §13 (Observability).
> Sibling specs: [0002_telemetry.md](0002_telemetry.md), [0004_errors.md](0004_errors.md).

## 1. Goal

Make the harness usable by a person watching it work.

The mechanics are sound and the surfaces are prototypes. `src/lumberjack/cli/main.py`
has 39 bare `print()` calls and no colour, no alignment, no exit codes. The dashboard in
`src/lumberjack/tui/dashboard.py` renders three tables and stops there.

The worst of it: **`lj run` prints one line and then goes silent for minutes.** A swarm
of agents editing your repository in the dark is not a tool anyone will trust twice.

## 2. Why now

Operators judge a coordination harness by whether they can tell it is coordinating. The
information already exists — every claim, conflict, negotiation turn and landing is an
event in the ledger — and none of it reaches the screen while it matters.

## 3. Design

### 3.1 Live progress during `lj run`

The headline change. The ledger is subscribable (`Ledger.subscribe(kinds=...)`), so
`lj run` should render a live view driven by that stream rather than waiting on the
final `StandOutcome`.

Minimum: a per-workstream line that updates in place, plus a scrolling event feed of
things a human actually cares about — a lease granted alongside a peer, a conflict
detected, a negotiation opening, an accord signed, a task landing or bouncing. Not every
event kind: `worktree_delta` fires constantly and belongs in a counter, not a feed.

Use `rich` (add it as a dependency) or Textual, whichever fits better with the dashboard
you are also building. Fall back to plain line-per-event output when stdout is not a
TTY, so `lj run > log.txt` and CI both stay sane.

### 3.2 The dashboard earns its keep

`lj watch` currently shows workstreams, conflicts and leases. Add, roughly in order of
value:

- **A conflict detail pane.** Selecting a conflict shows the oracle's evidence, the
  conflicting hunks and the negotiation transcript so far. This is the single most
  informative thing the system knows and it is currently only reachable through
  `lj conflicts --explain`.
- **The merge train**, with queue position and the current entry's gate stage.
- **An event feed**, filterable by kind.
- **A file heat map** — which paths the most workstreams are touching. This is the view
  that tells you your task decomposition was wrong.
- Keybindings beyond `q` and `r`: filter, pause the feed, jump to a workstream.

### 3.3 Consistent, structured output

Replace the bare prints with a small rendering layer:

- Colour by severity, reusing `Severity` (`notice` dim, `warn` yellow, `block` red).
- Align tables; truncate ids to 8 characters in tables but never in `--json` output.
- `--json` on `status`, `conflicts`, `board` and `replay`, for scripting.
- Real exit codes: `0` success, `1` partial (something blocked), `2` usage error,
  `3` no such stand. `lj run` must exit non-zero when a task is blocked, or it cannot
  be used in CI.

### 3.4 Fix the small sharp edges

- `lj init` writes the default gate commands (`ruff`, `ty`, `pytest`) into every repo
  regardless of language. Detect the project: `pyproject.toml` → the current defaults;
  `package.json` → the equivalent scripts; otherwise write an empty gate with a comment
  explaining what to fill in.
- `lj plan --dry-run` defaults to `True` and the flag does nothing else. Either make it
  meaningful or delete it.
- Every "no stands found" path prints a bare string. Say what to do next.
- `lj status` shows an integration head with no indication of whether anything landed.
- `lj watch` on a finished stand should say so rather than idling on a dead ledger.

### 3.5 Show the numbers

**0002 is adding usage accounting** — `UsageLedger.totals()` and `for_workstream()`.
Render them: tokens per workstream in the dashboard, a total on `lj run` exit. If that
work is not merged when you get there, build against the interface and leave the panel
empty rather than blocking; message that agent to agree the shape.

## 4. Acceptance criteria

- [ ] `lj run` shows live per-workstream progress and an event feed; a non-TTY stdout
      degrades to line-per-event.
- [ ] `lj watch` has a conflict detail pane showing evidence and any transcript.
- [ ] `lj status`, `lj conflicts`, `lj board`, `lj replay` all support `--json`.
- [ ] Exit codes as in §3.3, with tests.
- [ ] `lj init` detects the project type before writing gate commands.
- [ ] No bare `print()` remains in `src/lumberjack/cli/`.
- [ ] `uv run ruff check .`, `uv run ty check`, `uv run pytest` all clean.

## 5. Out of scope

- A web UI.
- Changing what the harness does. If a display needs an event that does not exist,
  that is a conversation with the other agents, not a unilateral change to the domain.
- Cost estimation in currency.

## 6. Tests

CLI tests are the gap in the current suite — `tests/` has no coverage of
`src/lumberjack/cli/` at all. Add `tests/unit/test_cli.py`: invoke commands against a
ledger built by the existing fixtures, assert on rendered output and exit codes. Use
`cyclopts`'s testing support, or call the command functions directly and capture stdout.

`tests/unit/test_render.py` — the rendering layer is pure: given a `Projections` and a
`StandOutcome`, assert the output. Keep formatting deterministic so these tests are not
brittle.

The dashboard itself needs at most a smoke test that it mounts and refreshes against a
replayed ledger; Textual snapshot testing is not worth the maintenance here.

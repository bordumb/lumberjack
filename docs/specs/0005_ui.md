# 0005 — The operator interface

> Builds on [0001_SPEC.md](0001_SPEC.md) §13 (Observability) and [0003_ux.md](0003_ux.md),
> which covers the terminal. This one covers the web interface in `site/`.
> House rules: [0000_house_rules.md](0000_house_rules.md).

## 0. House rules for this surface

The Python rules in [0000_house_rules.md](0000_house_rules.md) apply where they make
sense (dependencies, verification, wrap-don't-sprinkle). These are the ones specific to
`site/`:

- **TypeScript with no `any` and no `as` to escape a type.** The Python side is
  type-driven and the dashboard reads its data; a cast here re-introduces exactly the
  class of bug the domain models were built to prevent.
- **Design tokens, never hex.** `bg-background`, `text-muted-foreground`,
  `border-border`. The dashboard is dark by default and a hard-coded colour is a
  surface that stops matching the moment the theme moves.
- **shadcn/ui for chrome, Pierre for code.** Cards, badges, buttons and dialogs come
  from shadcn. Anything that displays *code* — a file, a diff, a merge conflict, a tree
  — comes from `@pierre/diffs` or `@pierre/trees`. Do not hand-roll either.
- **Verify by building.** `npx tsc --noEmit` and `npx next build` both pass before you
  claim anything. Ask the reader to check the visual result; do not claim it yourself.

## 1. First principles

Everything on screen is derived. There is no application database, and adding one would
create a second source of truth that drifts from the first.

| Surface | Read from | Written by |
|---|---|---|
| runs, workstreams, conflicts, notes, comments | `<repo>/.lumberjack/<stand>/ledger.db` | the harness |
| the repository tree | the working tree on disk | the person |
| an agent's transcript | `~/.claude/projects/<worktree>/*.jsonl` | the Claude Code CLI |
| which repositories exist | `~/.lumberjack/repos.json` | this interface |

That last row is the single exception, and it is config rather than derived state: it
holds paths a person chose, which is the one thing here that cannot be recomputed.

Four principles follow, and every decision below is one of them applied.

**1. Never assert a state you have not checked.** "Live" must mean a supervisor process
exists, not "nobody said otherwise". A crashed run and a working run are identical from
the ledger alone, so liveness reads a pid and falls back to whether the log is still
moving. The same rule governs review-comment status: `delivered` means the agent
actually read its inbox, never that time passed.

**2. The unit is the task, not the workstream.** A workstream is how a task was worked
on during one session; pausing and continuing gives a task a second one. Every signal —
deltas, leases, conflicts, transcripts — is keyed on the workstream, so reading one lane
shows a fraction of the work. `lib/weave.ts` is the only place lanes are combined, and
every surface reads the `TaskView` it produces.

**3. Mutations go through the CLI.** Posting a comment shells out to `lj comment`;
starting a run writes a `RunRequest` document and calls `lj run --request`. The shape of
a comment and the routing rule for who hears about it live in the Python domain, and a
second implementation here would be the one without validation.

**4. Show the whole thing, collapsed.** A transcript is mostly file contents and a note
is often a page. Nothing is truncated away; everything past five lines collapses with a
control that says how much is hidden.

## 2. The shell

`app/layout.tsx` holds a persistent left navigation. Every page renders inside it.

**The hierarchy is repository → run.** A repository shows its file tree; a run shows its
dashboard. The nav collapses to an icon rail and remembers the choice in `localStorage`.

- **Add project** sits at the top and opens a *server-side* folder browser.
  `showDirectoryPicker()` and `<input webkitdirectory>` both withhold the absolute path
  by design, and git needs one. The dashboard already runs on the same machine as the
  repositories it reads, so listing directories server-side is the trust boundary a
  terminal has, not a wider one. Only folders containing `.git` can be added.
- **A `+` on each repository row** opens the run composer: a name, then an agent per
  worktree, each with a prompt or a spec and its own provider and model. A run is often
  one strong agent and two cheap ones.
- **Runs nest under their repository** with a lifecycle dot — green live, orange stale,
  red halted, amber finished — and their goal, never a bare hex id.

## 3. The run dashboard — `/?stand=<id>`

Header: the run's name, its lifecycle badge, and the controls.

- **Pause** (red) appears only when the run is genuinely live.
- **Continue** (blue) appears when it is halted or stale. It resumes *in place* — same
  ledger, same task ids, same branches — because a run is a body of work rather than one
  process lifetime, and forking on every pause would make the unit of analysis the
  process.
- **A hamburger** holds Rename and Delete. Renaming adds a label; the log is append-only
  and the original goal stays in it. Deleting counts what it would destroy first, keeps
  branches by default, and refuses unlanded work without being told twice.

Below: four stat tiles, then one card per **task** (not per workstream) carrying files
touched, lines changed, leases, claims and idle time — all woven across sessions, with a
`2 sessions` badge when a task has been picked up again.

Then open conflicts, then the blackboard. Both are lists of links, never dead text.

---

## 4. The task page — `/agents/<workstream>`

A workstream id in the URL resolves to its **task**, and the page shows every session
that worked on it. The transcript is each session's log merged in order, with a labelled
divider at the seam rather than the seam smoothed over.

Each entry renders by what it is:

| Entry | Rendered as |
|---|---|
| a tool call | an icon, its label, and the file or command it acts on |
| a coordination call | the same, tinted with the primary colour |
| what the agent *says* | markdown (`components/prose.tsx`) — agents write tables |
| a coordination result | parsed structure (`lib/tool-result.ts`) |
| any other result | a Pierre `File`, highlighted in the language of the call it answers |

Two details that are easy to get wrong and were:

- **The `Read` tool prints its own line-number gutter.** Strip it, or it collides with
  the one the renderer draws and every line shows two numbers.
- **A result carries no language.** It inherits from the call it answers, so reading a
  `.py` file looks like Python instead of prose.

---

## 5. The conflict page — `/conflicts/<id>`

One page per raised conflict: severity, source, a plain-English explanation of what that
source *means*, the oracle's evidence, and one collapsible section per contested file.

Which surface a file gets depends on the trouble it is in:

- **Genuinely clashing** — three-way merged with `git merge-file --diff3`, then rendered
  through Pierre's `UnresolvedFile` with `mergeConflictActionsType: "default"`, so the
  real conflict regions appear with take-one-side controls.
- **Merges cleanly as text** — which is most of a `blast_radius` conflict, where the
  danger is semantic. Each side gets a **split** `MultiFileDiff` against the base they
  diverged from, which is exactly what git merged.

---

## 6. The note page — `/notes/<id>`

Agents write markdown, and a three-line clamp on the dashboard hides the part that
matters. Each note gets a page: rendered body, source one click away, and the scope that
decides who it reaches — the blackboard is scoped rather than broadcast. A note with no
scope says so, because that means it competes for every agent's context budget.

---

## 7. The repository browser — `/`

`@pierre/trees` over a flat path list, with `git status` decorations.

**Read the working tree from disk, not `git ls-files`.** The obvious first
implementation omits everything gitignored, which is exactly `.venv`, `.hypothesis` and
`.lumberjack` — and `.lumberjack` is where the runs live, so a tree that hides it is
useless for inspecting one by hand. Ignored paths are *included and marked ignored*.
Only `.git` and `node_modules` are skipped, and neither is a judgement about importance:
one is object storage, the other 30,000 files nobody browses.

Selecting a file opens it in a Pierre `File` beside the tree.

## 8. Component vocabulary

Reuse these. A second component that does the same job is a second set of behaviours to
learn.

| Component | Responsibility |
|---|---|
| `code-snippet.tsx` | any code or diff in a log: collapse, hover, gutter `+` |
| `prose.tsx` | markdown, styled once, used by notes and agent messages |
| `agent-message.tsx` | prose plus collapse, for what an agent says |
| `tool-result.tsx` | structure recovered from a coordination result |
| `comments.tsx` | composer, card, status ladder, and the `Anno` annotation shape |
| `gutter-add.tsx` | the `+` affordance, shared by every code surface |
| `token-hover.tsx` | signature on hover, from the repo-wide index |
| `tool-icon.tsx` | tool name → icon, and which tools count as coordination |

### Icons

`lucide-react`, `h-3.5 w-3.5` inline and `h-4 w-4` for controls. The map lives in
`tool-icon.tsx` and exists so the same action always looks the same:

| | | | |
|---|---|---|---|
| Read | `BookOpen` | join | `LogIn` |
| Write | `PenLine` | awareness | `Radar` |
| Edit | `Pencil` | claim | `Lock` |
| Run | `Terminal` | release | `Unlock` |
| Search | `Search` | who_touches | `Users` |
| Glob | `FolderSearch` | check_merge | `GitMerge` |
| Plan | `ListChecks` | request_land | `GitPullRequestArrow` |
| Delegate | `Bot` | post_note | `StickyNote` |
| anything else | `Wrench` | message | `MessageSquare` |

**Coordination tools are tinted `text-primary`; file work stays muted.** That contrast is
the whole point: it is how a reader sees at a glance whether an agent is participating in
the swarm or only editing files.

## 9. Pierre, specifically

Read the skills in `.agents/skills/diffs` and `.agents/skills/trees` before using either.
Four things cost real time to discover:

1. **The two gutter APIs are mutually exclusive.** Passing both `onGutterUtilityClick`
   and `renderGutterUtility` is a runtime error. Use `renderGutterUtility` and handle the
   click inside your own button, reading the line from the `getHoveredLine` callback it
   hands you.
2. **Comment composers must be line annotations.** Rendering one in a block beside the
   diff makes the reader hold a line number in their head. Both a posted comment and an
   open composer are annotations on the same line — one `Anno` type carries either.
3. **Token hover goes through the renderer's own token events**, not DOM listeners, so it
   survives virtualization. Index definitions **repo-wide** with one `git grep`: the names
   worth explaining are the ones a file *imports*, and those are never defined on screen.
4. **`diffStyle: "split"`** for conflicts and diffs, `theme: "pierre-dark"` throughout.

## 10. The font trap

`shadcn init` writes `--font-sans: var(--font-sans)` into `globals.css` — a circular
self-reference. Tailwind v4 resolves `@theme inline` at parse time, so it cannot see a
font variable Next injects at runtime either. Literal family names are the only thing
that works, and without them every heading silently falls back to Times.

```css
--font-sans: "Geist", "Geist Fallback", ui-sans-serif, system-ui, sans-serif;
--font-mono: "Geist Mono", "Geist Mono Fallback", ui-monospace, monospace;
```

## 11. Acceptance criteria

- [ ] Every page renders inside the collapsible nav, and its state survives a reload.
- [ ] No surface reads a single workstream where a task has several; `weave.ts` is the
      only place lanes are combined.
- [ ] `live` is only shown when a supervisor process exists.
- [ ] Every mutation goes through `lj`; nothing writes the ledger from `site/`.
- [ ] Code, diffs and trees come from Pierre; chrome comes from shadcn.
- [ ] Anything past five lines collapses, and says how much is hidden.
- [ ] `npx tsc --noEmit` and `npx next build` both pass.

## 12. Out of scope

- Authentication. This is a local tool on the machine that owns the repositories.
- Editing code in the browser. The agents have worktrees; this surface is for reading
  and for the few decisions a person makes.
- Rendering anything the harness does not already record. If a view needs data that does
  not exist, that is a conversation about the domain, not a new query here.
